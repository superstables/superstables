# `superstables budget` CLI contract

`budget` keeps the 0.3.0 command-completion meaning of `final`. It is `false` while an owner approval is open or a buy-once `unknown` can still be read by `wait`, and `true` otherwise. `chain_final` describes the current matching payment separately: `true` after chain finality, `false` while included but not final, and `null` when no current matching inclusion is established, including an unknown after removal. A provisional paid purchase is `settled`, with `final: true`, `chain_final: false`, and exit 0 when delivered or exit 4 when not delivered. Check finality later with `reconcile` or `wait`; never pay again for that purchase. Owner-command transactions are not seller payments and have `chain_final: null`. Older stored results without finality evidence also have `chain_final: null`.

One command for the budget rails. `superstables budget` is a thin dispatcher over the rail scripts, which follow `CONTRACT.md`. It normalizes their `RESULT` lines into one shape. `buy-once` is the other way to pay: one purchase the owner approves on superstables.com, with no budget. Testnet only. Test tokens, no real money.

| `--rail` | Path | Chains (`--chain`) | Implementation |
| --- | --- | --- | --- |
| `evm` | plain approve, pull then pay | `base-sepolia` (default), `arc-testnet`, `arbitrum-sepolia`, `polygon-amoy`, `skale-base-sepolia`, `ethereum-sepolia`, `robinhood-testnet` | `evm/` |
| `tempo` | access key, MPP charge | `moderato` (default, the only one) | `tempo/` |
| `solana` | SPL delegate, x402 | `devnet` (default, the only one) | `solana/` |

Chain to rail: Base Sepolia, Arc Testnet, Arbitrum Sepolia, Polygon Amoy, SKALE Base Sepolia, Ethereum Sepolia and Robinhood Chain Testnet are `evm`; Tempo Moderato is `tempo`; Solana devnet is `solana`.

The owner's steps, in order, once per rail and chain: `evm` and `solana`: `setup`, `fund-agent`, `doctor`, `grant`; `tempo`: `setup`, `grant`. `fund-agent` sends the agent key funds for network fees only (the chain's gas token on `evm`, native USDC on Arc Testnet; SOL on `solana`); it does not grant a budget. The grant leaves the funds in the owner's wallet: an allowance on `evm`, a delegate on `solana`, an access key limit on `tempo`. An agent may start any owner command and hand the owner the approval link; only the owner approves.

## Help

`superstables budget --help` is enough to use the tool without this file: a start-here sequence for the owner and for the agent, the rails and their `--chain` values with the defaults, the chain-to-rail map, the owner's steps per rail, the commands with who runs each and whether it moves money, owner approvals, the `RESULT` fields, the exit codes and where state lives. Every command's `--help` has the same parts in the same order: usage, what it does, the `--chain` values (when it takes `--chain`), `Moves money:`, `Run by:`, `Example:`, `Prints:` and `Exit codes:`. `buy --help` also says what `--max` is and what must exist before the first buy, and how to check it.

## Commands

| `superstables budget setup --rail R [--chain C] [--new-owner] [--hosted [--site URL] [--grant A] [--fund [AMOUNT]]]` | owner | Creates the agent key file if it is missing (never overwrites it). With `--hosted`, the owner adds this agent to their superstables.com account instead, and the chain's owner approvals happen on superstables.com from then on (see [Approvals on superstables.com](#hosted-approvals)); with `--grant A` and `--fund` (not on `tempo`), the same approval link also asks for the agent's gas and a budget of A. A trusted step: the signature proves control of an address, not the owner's identity, so whoever completes setup becomes the owner on record. The owner runs it, or watches it run: an agent may start it and hand the owner the approval link, but never completes it. Running it again reuses the agent key. A recorded owner never changes silently: `--new-owner` replaces it, refused (exit 3) while a budget is live on it. On `solana` and `tempo` an owner is on record when the public file or the agent key file names it; when the two name different owners, setup and `revoke` refuse (exit 3) until `--new-owner` records one again. `--new-owner` is refused while a budget is live on either, and names the owner who must revoke it and how: through `revoke` when it can target that owner and key and the owner files do not disagree, otherwise through a transaction signed in that owner's own wallet. A completed setup writes the owner into both files. `tempo`: also tops up the owner from the Moderato faucet when it holds less than 1 pathUSD (`--fund-only` tops up the owner on record again and does nothing else: no page, no file changed, refused with `--hosted`, `--grant` or `--fund`), and `--agent LABEL` adds a new agent key (no page; on a chain with approvals on superstables.com, one approval link that adds the new key). |

Prints what to top up at which address. No transactions. No rail has an owner key file to check. On `evm` the gas minimums grow with the current fee: the agent needs twice what one purchase plus a failed one's cleanup (pull, cancel, return) costs now, and doctor prints that cost. |

The price is the seller's ask, not a ceiling: `next` leaves `--max` to the caller. Needs no setup. Sends one unpaid HTTP request to read the seller's terms; **signs nothing and submits no payment**; opens no key file. `--url` must be `https`, or `http` on this machine; anything else is refused (exit 2). |
| `superstables budget grant --rail R --amount A [--expiry ISO] [--period S] [--sellers a,b]` | owner | Prints the terms (cap, true maximum, what the chain enforces and what it doesn't). The owner approves it on the approval page. Refuses constraints the rail can't enforce (`evm` and `solana`: `--expiry`, `--period`, `--sellers`). |
| `superstables budget status --rail R` | anyone | Remaining budget, expiry, revoked, funds at risk. No secrets. With no setup on this machine (no agent key, or no owner connected) it says so first, before any chain read: exit 1, `reason` "no budget has been set up here for R on C: ...", `home` the client home it checked, and `next` the owner's commands in order, then that if the budget is elsewhere the agent asks the user for the path instead of changing `SUPERSTABLES_HOME` or looking in another home itself (`~/.superstables` included). stderr names the home and the files it looked for. `remaining` 0 or a revoked budget: exit 0, and `next` says what is next. `tempo` also has `expired`, and `refillsAt`: the end of the current period of a live period budget, when the limit refills (`null` otherwise; it does not mean nothing is left). `revoked` is `true` only for a revoke this machine recorded that the chain still shows: on `evm` an allowance of 0 with `B4_REVOKED_AT` in the public file (written by `revoke` and `recover`), on `solana` no delegate with `REVOKED_AT` (written by `revoke`; a grant or a new owner removes it), on `tempo` the keychain's own revoked flag. An allowance or delegate that reads 0 without that record is `remaining: "0"`, `revoked: false`: spent, never granted and revoked elsewhere look the same on chain. |
| `superstables budget buy --rail R --url U --max M [--pay-to ADDR] [--op ID] [--method M --body JSON]` | agent | One purchase under the budget. `--max` is the most this one purchase may cost, in the budget token (`0.02` is 0.02 USDC, or pathUSD on tempo); a higher price is refused before signing. `--method` and `--body` are for tempo and solana. On `evm`, the seller's answer to the paid request is saved as a file (see Output). Needs `setup` and `grant` (and on `evm` and `solana` gas from `fund-agent`); see "A buy with nothing to buy with" below. On `evm`, nothing is signed unless the agent key can pay, at the current fee, the gas for the pull and for the cancel and return a failed purchase would need: otherwise `refused_precheck` (exit 3), with `next` naming `fund-agent`. `--url` must be `https`, or `http` on this machine; anything else is refused (exit 2). |
| `superstables budget buy-once --service ID --max M [--param K=V ...] [--params JSON] [--site URL] [--wait \| --detach] [--replace]` | agent, owner approves | One purchase of a service the site lists for it, approved by the owner on superstables.com: no setup, no budget, no agent key (see [Single purchase on superstables.com](#buy-once)). On Base Sepolia, Arc Testnet, Tempo Moderato or Solana devnet, as the listing says. `--service` and `--max` are required. |
| `superstables budget unlock --rail R [--chain C] --op ID --confirm [--unverified]` | owner or operator | Owner recovery after stopping all work on the operation. Plain `--confirm` requires proof that the lock's processes have stopped. If that cannot be verified, the owner can use `--confirm --unverified` in their own terminal and type the operation ID followed by `unverified`. Clearing a lock while a process can still run may allow a second payment. Preserves the journal. Reconcile next. |
| `superstables budget unlock --cap` or `--attempt ID` or `--buy-once`, or `--rail R [--chain C] --approvals` or `--approval ID`, or `--rail evm [--chain C] --agent-key`, with `--confirm [--unverified]` | owner or operator | Recover a core payment lock, approval lock, attempt runner or start lock for a single purchase after stopping all payment work. `--agent-key` recovers the lock that makes purchases on one agent key take turns. Requires a terminal and the exact `payment-lock` confirmation (`agent-key` for `--agent-key`). Preserves payment evidence. Check the original attempt or approval next. See [Other payment lock recovery](#other-payment-lock-recovery). |
| `superstables budget reconcile --rail R --op ID` | anyone | Reads the chain for an operation. **Never signs or sends.** |
| `superstables budget recover --rail evm [--op ID]` | owner | EVM only: stop the allowance first, then return stranded funds. The agent key signs its own steps. The owner approves `approve(agent, 0)` on the approval page unless the agent's own revoke in this run brought the allowance to 0 and a later read shows 0, and gas for the agent when it has too little. A purchase's price goes back only once its authorization can no longer settle at a final block; a cancellation that is not final yet leaves the price in the agent key and the outcome `unknown`. Without `--op`, recover lists, one per line in its output, every journal it cannot read and every operation of the agent that can still move money (the rail script's RESULT carries them as `unreadable` and `undecided`), and then skips the sweep: `unknown`, exit 5. |
| `superstables budget revoke --rail R` | owner | Ends the budget on chain. The owner approves it on the approval page. It sends the revoke every time it is asked, even when the budget already reads empty or revoked, and, when it sends a transaction, reports `revoked` only after its own transaction and a read that shows it: one RPC's read is not proof that nothing is live. The one exception is `tempo`, below, where nothing is sent. `evm`: `approve(agent, 0)`. `solana`: the SPL `Revoke`, unless the owner has no USDC account (nothing sent: exit 0, `state: "ok"`, `revoked: null`). `tempo`: `revokeKey`, unless the key reads revoked or never authorized and the keychain refuses a simulated `revokeKey` from the owner (`KeyAlreadyRevoked` or `KeyNotFound`). Then nothing is sent: a key that reads revoked is `state: "ok"`, `revoked: true`, `tx: {}`, and one never authorized is refused (exit 3). A simulation that cannot be read is `unknown` (exit 5), with nothing sent. This `revoked` is the command's own result; `status` reports `revoked` by its own rule (see its row). |
| `superstables budget find [--rail R] [--chain C] [--once] [--site URL]` | anyone | Lists the services superstables.com says a budget can pay (`GET /api/v1/budget/services`): name, price, chain (the `--chain` key when the client knows the chain), simulated and URL, as a table on stdout; `RESULT` carries them as `services` (with `--json`, stdout is that object alone). `--rail R` or `--chain C` lists only that rail or chain: every key the budget commands take works, `moderato` (tempo) and `devnet` (solana) as well as the `evm` chains; an unknown one is refused (exit 2) with every valid key. `simulated` is `true` (`yes` in the table) when the listing says the service returns prepared sample output, `false` (`no`) when the listing marks it as not sample output (this does not verify that the data is real), and `null` (`not said`) when the listing does not say; the client reads the site's `simulated`, `mock` or `sample` field. When the site has no list, it exits 1 and `next` says that any seller URL works with `preflight` and `buy`. The site is `--site`, else `SUPERSTABLES_SITE`, else the `SITE` that `setup --hosted` recorded (for `--rail` and `--chain` when given, else the first chain that has one), else `https://www.superstables.com`. Reads only; no account, key or rail. With `--once`, it lists instead the services that can be bought once (`GET /api/v1/purchase/services`): `id`, `price`, `simulated`, `network` and `inputs` (`*` marks a required one); `RESULT` carries them as `services`. `--rail` and `--chain` narrow it the same way. |
| `superstables budget wait --id ID --shown [--timeout S] [--site URL] [--abandon]` | anyone; `--abandon` the owner only | After a detached owner command or `buy-once`: waits up to `S` seconds (default 30, at most 300) and prints the approval's state, with `final` (`false` while `waiting_owner`, or while a buy-once `unknown` can still be read). `--abandon` gives up a buy-once purchase the site never ends (see [Single purchase on superstables.com](#buy-once)). `--shown` says the approval link, the match code and the terms were written in a reply the owner can read; without it `wait` refuses (see [Detached or blocking](#detached-or-blocking)). **Never signs or sends.** |

On tempo, `--agent LABEL` picks the access key for `doctor`, `grant`, `status`, `buy` and `revoke`, and `setup --agent LABEL` makes a new one. A label is 1 to 40 letters, digits or underscores, the same in every command. `setup --agent` never replaces a key the public file already records under that label (exit 3): pick another label.

Every command: `--help` exits 0 and bad input exits 2 before any secret is read. `--mainnet` or a mainnet chain id is refused.

`--site URL` is accepted by every command. It must be an origin: `https://superstables.com` or one of its subdomains (such as `https://staging.superstables.com`), or this machine (`http` or `https` on `127.0.0.1`, `localhost` or `[::1]`). Any other origin is refused (exit 2) unless the owner has named that exact origin in `SUPERSTABLES_ALLOW_SITE` (an origin, or a comma-separated list; `https` only) in their own environment. That setting is the owner's: an agent never sets it. The same check applies to `SUPERSTABLES_SITE` and to a `SITE` recorded in a public file (an owner command refuses a recorded site that no longer passes it). Where a site is recorded, a different one is refused (exit 2, nothing read or sent): for a command on a chain set up with `--hosted`, the site recorded in that chain's public file; for `wait`, the site the approval was made on. `setup --hosted` and `find` use `--site` to choose the site, and `buy-once` uses it to choose where to buy. Everywhere else it is checked and ignored.

## Owner approval

`setup`, `fund-agent`, `grant`, `revoke` and, on `evm`, the owner's part of `recover` use the owner's wallet by default. The explicit test key-file option is described below. The rail script builds the transaction and the terms, starts a page on `127.0.0.1` (random port, one-time random id in the path), and waits. The owner opens the page in the browser with their wallet, connects, and approves or rejects. For transactions, the script checks the chain before the final `RESULT`. Setup verifies a message signature and records the address. Detached commands first return a pending `RESULT`.

| Rail | Wallet | What the wallet does | What the command reads back |
| --- | --- | --- | --- |
| `evm` | EVM browser wallets found through EIP-6963 or `window.ethereum`; accepted transaction forms are described below | Sends `{to, data, value}`, itself or through the owner's smart account (see below) | The owner's call (target, exact data, value), receipt, the effect (`Approval(owner, agent, amount)`, `Transfer(owner, agent, amount)`, or the agent's balance for gas), the allowance |
| `tempo` | Any EVM browser wallet that can add a custom chain, found the same way | Is asked to send a call to the AccountKeychain precompile (`authorizeKey` or `revokeKey`) with the owner paying the fee in their configured fee token, or pathUSD by default. The page adds Tempo Testnet (Moderato) with 18 decimals. | Sender, target, exact data, fee payer, receipt; then the key: type, expiry, limit, period, seller list, not an admin key; or revoked |
| `solana` | Any Solana wallet (Phantom, Solflare, Backpack, ...), found through the Wallet Standard | Only signs. The command builds the transaction when the owner presses Review in wallet, checks that the signed message is byte for byte its own (or its own with one compute unit limit and one unit price put first, a priority fee of at most 0.001 SOL) and signed by the owner, then sends it. | No error, signer the owner; then the token account: owner, mint, delegate and delegated amount (or no delegate); or the agent's SOL |

With more than one wallet installed, the page lists them and the owner chooses one. The page then uses only that wallet.

On `evm`, a wallet may pay the network fee for the owner: MetaMask then has a relayer send the step through MetaMask's DelegationManager, and the owner's account makes the call. The command accepts that only on a chain where the client pins the manager's code (Base Sepolia, Arc Testnet, Arbitrum Sepolia, Polygon Amoy, Ethereum Sepolia), when the code at the manager's address in that block is the pinned code and the receipt has the manager's one `RedeemedDelegation` event for the owner and the transaction's sender. For a gas top-up sent this way, which leaves no log, the owner's address must have run MetaMask's pinned smart-account code in that transaction, read from its code and nonce before and after the block. On SKALE Base Sepolia and Robinhood Chain Testnet, only a transaction the owner sends itself counts. Anything else is a mismatch: `unknown` (exit 5). When a required chain read is unavailable, the reads cannot establish which smart-account implementation ran during a sponsored gas top-up, or the agent's balance does not show the required increase, the result is `unknown` (exit 5), never settled.

### Approvals on superstables.com

`setup --rail R --hosted [--site URL]` moves a chain's owner approvals to superstables.com, on every rail: `evm`, `tempo` (Moderato) and `solana` (devnet). The owner needs a superstables.com account, created by signing in with an Ethereum or Solana wallet. For now, a Solana account supports only Solana agents, Solana budgets and Solana single purchases. With an Ethereum account, Solana actions also need a Solana wallet to sign transactions. The page on `127.0.0.1` needs no account, and stays the default.

- Setup sends an add-agent request (kind `link`), signed by the agent key (proof v2: EIP-191 on `evm` and `tempo`, ed25519 on `solana`, over a text that names the site's origin and a single-use nonce). The owner opens the approval link on any device where they are signed in to the site with their wallet, picks the match code the agent showed them, and signs the owner-proof message with their wallet (no fee). The command rebuilds that text from its own values and checks the signature before it records anyone; an add-agent request without a valid owner proof records nothing (exit 3). The owner on record becomes the address that signed (`B4_OWNER_ADDRESS`, `OWNER_ADDRESS` on `tempo`); on `solana`, the Solana address the owner connects and signs with on that page (`SOLANA_OWNER_ADDRESS`). The public file gets `APPROVALS=hosted`, `SITE=<origin>` and the add-agent request the owner signed: `LINK_ID` and `LINK_CODE` (on `tempo`, a key added with `setup --agent LABEL` gets `AGENT<LABEL>_LINK_ID` and `AGENT<LABEL>_LINK_CODE`). A different recorded owner is replaced only with `--new-owner` (refused while a budget is live and, on `evm`, while the agent key holds the budget token, which `recover` would return to the owner on record).
- Run again for an agent the site has already added on that chain, setup takes the site's `already_linked` answer only for the owner recorded on this machine, without `--new-owner`, on the site recorded with it, and only when the answer carries the owner's proof over the stored `LINK_ID` and `LINK_CODE`. Anything else is refused (exit 3) and records nothing: the owner removes the agent on their account page on the site and adds it again. Moving a chain with approvals on superstables.com to another site therefore means adding the agent there, with a new owner proof.
- From then on `grant`, `revoke` and `fund-agent` on that chain go to the site as an approval request, signed by the agent key. On `solana` and `tempo`, when a `revoke` on superstables.com needs approval but the agent key file is missing or cannot be used, it refuses (exit 3, nothing requested) and names where to revoke without it: Revoke on the owner's account page on the site, or a revoke transaction signed in the owner's own wallet. `evm` and `tempo` send the exact transaction (`tempo`: `authorizeKey` or `revokeKey` on the keychain). `solana` sends the amount only (`solana: {amount_atomic}`; none for a revoke): the site builds the transaction when the owner is ready, the owner's Solana wallet signs it and the site sends it. On `tempo`, `setup --agent LABEL` adds the new key with one approval link, and `grant --agent LABEL` is signed by that key. The owner's wallet sends it from the site's page. Every request is refused (exit 3, nothing sent) when the site would act for another address than the owner on record. The command then reads the chain exactly as with the local page, and refuses a mismatch the same way: the same `RESULT` and exit codes. On `solana`, where the site built the transaction, the command also checks that the owner signed and paid the fee, after the request started, as the only signer, with no address lookup tables, and that its instructions are exactly the one the command would have built (`ApproveChecked` with the owner's USDC account, the mint, the agent, the owner, the amount and 6 decimals; `Revoke`; or the System Program transfer of exactly the lamports to the agent), plus at most one compute unit limit (10,000 to 1,400,000) and one unit price whose fee is at most 0.001 SOL: the same bounds the page on this machine accepts from a wallet. Anything else is a mismatch (`unknown`, exit 5), and the owner revokes. On Arc, where USDC pays the fees, `fund-agent` (on this machine or on superstables.com) asks for a plain transfer of native USDC to the agent (the value in 18 decimals, no data), not the ERC-20's `transfer`; the command then checks that transaction and the agent's native balance. A transaction the site reports as `failed` is read from the chain too and is never settled: it is `failed` only when it reverted and matches the plan, otherwise `unknown` (exit 5).
- `setup --hosted --grant A --fund [AMOUNT]` is the whole set-up with one approval link. The add-agent request carries `then`: the gas transfer (`fund_agent`, AMOUNT or `fund-agent`'s default for the chain) and the grant of A, built as `fund-agent` and `grant` build them, in that order (`solana`: the amounts; `tempo`: the grant only, for 24 hours). After the owner adds the agent, the site's page asks their wallet for each. The command records the owner as above, then reads each transaction from the chain with the same checks as `fund-agent` and `grant` (receipt, the owner on record made exactly the planned call, mined after the block it read before the request, with its effect: see below), and records the budget only when the allowance reads exactly A. A step the site reports as `failed` is never settled, whatever the chain shows. The final `RESULT` has `linked` and `steps` (`kind`, `state`, `tx`, `amount`, `reason` for each) and `tx` (`fundAgent`, `grant`). When a step did not complete (the owner rejected the grant, say), the agent stays added and recorded. While no step's wallet was asked, `state` is the first such step's, `refused_precheck` (exit 3). Once one was, `state` is `failed` (exit 1, with `proof`) only when that step's transaction failed in a way the chain proves and no other step may have moved funds; otherwise it is `unknown` (exit 5), also after a refusal of a later step, with each step's own state in `steps` (a step whose own state is `mismatch` reads `unknown`). When a step landed and a later one then failed in a way the chain proves, `reason` starts with `partly_done` and names both. If the command stops waiting after the agent is added, it withdraws on the site the steps the owner's wallet has not been asked for, and reports them as not sent only once the site confirms it; a step it could not withdraw is `unknown` (exit 5). Either flag alone is accepted; without `--hosted` both are refused (exit 2). An agent the site has already added on that chain is refused (exit 3, `already_linked`): gas and a budget then go through `fund-agent` and `grant`.
- `recover` keeps the page on this machine for its owner steps. `setup` without `--hosted` keeps the recorded owner and mode; `setup --new-owner` without `--hosted` moves the chain back to the local page.
- The approval link is used only as `<site>/approve/budget/<the request id>#<token>`, written again by the URL parser; an answer whose URL has control characters, spaces or invisible characters, another path or a query is refused before anything is shown. When the site is not `www.superstables.com`, the stderr text and `message_for_owner` name its host.
- `APPROVE` and `RESULT` carry `matchCode`. The agent writes it next to the approval link in its reply to the owner, a visible message, not only in its reasoning or a tool call. The agent writes the approval link and code in its reply and ends its turn; `wait --shown` then reads the request's state from the site; `--replace` asks the site to cancel, which it does only while the wallet has not been asked.
- The site's access token for polling a request (`ssbt_...`) is stored only in that approval's record (mode 600) and removed when the approval is final. It is never logged.
- A site that cannot be reached, or that refuses the request (for example a cap above the account's limit), is a refusal before anything is sent: exit 3, with the HTTP status when available and any supplied error code, shown only if documented or replaced with `unexpected`. Once the site reports that the wallet was asked, or a transaction hash, an unfinished outcome is `unknown` (exit 5), never "nothing sent".

- As soon as the approval link exists, stdout gets one line `APPROVE {"action","url","expires","terms"}` (on superstables.com: also `matchCode`; stderr with `--json`). `terms` holds the page's plain words: `title`, `amount`, `unit`, `summary`, `enforced`, `notEnforced`. The same approval link goes to stderr in words. The `APPROVE` line is printed once per approval link: the dispatcher does not echo the rail script's own `APPROVE` or `RESULT` lines, or a background worker's, to stderr. The final `RESULT` is still the last line, and carries `url`.
- The sentence on stderr that carries the approval link, and the `next` of a `waiting_owner` result, say: `Testnet only. Test tokens, no real money.` The stderr sentence for an approval link on superstables.com also says that the first approval link the owner opens asks them to sign in with their wallet (a message, no fee).
- The local page listens on `127.0.0.1` only. Over SSH the owner forwards its port first, `ssh -L PORT:127.0.0.1:PORT user@host` with the port from the approval link; the stderr text and the `waiting_owner` `next` show that command with the real port.
- `--timeout SECONDS` (10 to 3600, default 600): how long the approval link stays open. One that expires before the wallet was asked to send ends the command `refused_precheck` (exit 3), with nothing sent by that approval. In `recover` or a setup on superstables.com with `--grant` or `--fund`, an earlier step may have completed. Check any `steps` and `tx` in the result, and run `superstables budget status`. `next` says to run the same command again for a new approval link (`setup` reuses the agent key it created). `--no-open`: do not open it in the default browser. Detached, the approval link opens in the default browser too, except over SSH (`SSH_CONNECTION` or `SSH_TTY` set), where it would open on the remote host.

### Detached or blocking

An agent's shell tool usually shows output only when the command exits, and many tools stop a command after a minute or two. So an owner command has two modes:

| Mode | When | What happens |
| --- | --- | --- |
| Detached | stdout is not a terminal (an agent), or `--detach` | The command starts itself again as a background process and returns as soon as the approval link exists. It prints `APPROVE`, then `RESULT` with `state: "waiting_owner"`, exit 0, and `id`, `url`, `expires`, `terms` and `next`. The worker opens the approval link in the default browser (unless `--no-open`, or over SSH). |
| Blocking | stdout is a terminal (a person), or `--wait` | As before: the command opens the approval link in the default browser (unless `--no-open`), waits for the owner, reads the chain and prints the final `RESULT`. |

Then `superstables budget wait --id ID --shown [--timeout S]` polls the approval. The `next` of every command that returns `waiting_owner` (`setup`, `grant`, `revoke`, `fund-agent`, `recover`, `buy-once`) says: write the approval link, the code and the terms in your reply to the owner, then run `superstables budget wait --id <id> --shown`. `--shown` means the caller has done that. Without it, `wait` refuses before it reads anything: exit 2, `RESULT` with `state: "show_owner_first"`, the same `id`, `url`, `matchCode`, `expires` and `terms`, and a short `next` that says this wait did not read the approval, so whether the owner approved or paid is not known. An approval that has already ended returns its final `RESULT` without `--shown`, and so does one the owner already acted on: an owner command whose page log shows the owner's wallet was asked to send, or a buy-once purchase an earlier read showed payment evidence for. `wait` then reads it as with `--shown`. An unknown `id` is exit 2 as before.

- Still open: `RESULT` with `state: "waiting_owner"`, `final: false`, exit 0, the same `id`, `url`, `expires` and `terms`, and a `reason` describing the recorded page state (for example "the owner account is selected; waiting for wallet approval"). Once the page, the site or the page log says the owner's wallet was asked to send, the open approval is `unknown` instead: `final: false`, exit 5, `id` and `url`, and a `next` that says to tell the owner the outcome is unknown, start no other owner command, and run `wait --shown` again later for the final result. `recover` can ask the owner twice (the rest of the allowance, then gas for the agent). A new approval link ends the wait at once, with the new `url`: write it before polling again.
- Ended: the owner command's own final `RESULT` and exit code, exactly as the blocking command prints them, plus `id` and `final: true`: `settled` with the `tx` the command read from the chain, `refused_precheck` (exit 3) when the owner rejected or the approval link expired before the wallet was asked to send, `unknown` (exit 5) when the wallet may have sent (including a rejection reported after it was asked) or the transaction on chain did not match the plan. Later `wait` calls return the stored final result. Waiting never approves the request or retries a transaction.
- The background process ended without a `RESULT` (killed, or the machine restarted): `refused_precheck` (exit 3) when its last page log has no recorded submission, else `unknown` (exit 5).
- An unknown id exits 2.

Run one owner command at a time per rail and chain. Detached and blocking owner commands (and `--owner-key-file ... --yes`) take the same lock, created in one exclusive step. A tracked pending approval causes another command to be refused (exit 3). Do not use another terminal or client home to start a parallel approval. Its `RESULT` carries the pending `id` and `url`, and `next` says to run `wait --id`. `--replace` asks the pending page to cancel. The page answers in one step: if the wallet was never asked, the old approval ends as `refused_precheck` with a reason that names the new id, its processes are stopped, and the replacement starts. If the wallet was already asked, the replacement is refused and the old approval stays pending. Use it only at the owner's request, after cancelling any wallet prompt. It cannot cancel a transaction already submitted.

Each owner command's rail script runs in its own process group, recorded with the approval (the page's process runs in it). If the background worker dies while its page still runs, `wait` keeps returning `waiting_owner` (or `unknown` once the wallet was asked) with a reason that says so, and the chain stays held. Past the approval's deadline `wait` stops that group itself. Only when no process of it is left does `wait` record a final result from what the page logged: `unknown` (exit 5) if the wallet had been asked to send, `refused_precheck` (exit 3) otherwise.

The background worker has a timeout. The page expires its approval link after `--timeout`. A wallet that was asked to send gets 2 more minutes to report the hash, and the chain reads are bounded. A backstop stops the process after `--timeout` plus 9 minutes, with `unknown` (exit 5). The timeout runs without `wait`. It does not cancel a wallet request or a submitted transaction.
- A rejection or expiry before the wallet was asked to send returns `state: "refused_precheck"`, exit 3. Once the page asked the wallet to send, a reported rejection cannot prove nothing was submitted (anyone holding the approval link can post it, and a wallet prompt may still be open): the result is `state: "unknown"`, exit 5, as when no hash came back. Read `status` before trying again.
- `evm` and `tempo`: the command reads the reported transaction from the chain. A different sender, target, calldata, value, chain, a block before the request, a transaction type other than a plain one (`tempo`), or a fee payer other than the owner (`tempo`) is a mismatch: `unknown`, exit 5, with a reason naming each difference and a next step to revoke, even when the allowance or key reads right afterwards. A requested `tempo` period must read back exactly. If the owner's fee token cannot be read, `tempo` refuses before any approval link instead of assuming pathUSD.
- The approval page's state-changing routes accept only requests from the page's own origin with a JSON body. That stops other web pages in the owner's browser; it is not authentication of a person. Every owner page shows the recorded owner address.
- The chain shows something other than the plan (on `evm` an allowance other than the cap, because the owner edited the spending cap in the wallet; on `tempo` another limit, expiry or seller list; on `solana` another delegate or amount): `unknown`, exit 5, since the owner's transaction made a change that was not planned; revoke it.
- `solana`: a wallet that changed the transaction (another amount, an added instruction) gets nothing sent. The page says so and stays open; the command logs the program ids the wallet added. A transaction the owner signed after its blockhash expired (about a minute) is not sent either: request a fresh transaction with Review in wallet only after the command confirms it did not submit the old one. Any error from the wallet's sign call ends the approval as a rejection.
- `--yes` without `--owner-key-file` exits 2, on every rail.
- Tests and automation only: `--owner-key-file PATH` (mode 600) with `--yes` signs with that key file instead. `setup --owner-key-file PATH` records its address.

## Single purchase on superstables.com

`buy-once` wraps the site's purchase API on superstables.com (`GET /api/v1/purchase/services`, `POST /api/v1/purchases` with an `Idempotency-Key` and `{service_id, params, max_amount}`, `GET /api/v1/purchases/{id}?wait=...`, `POST /api/v1/purchases/{id}/cancel`; the site documents it at `/docs/purchase.md`). Testnet only. The chain comes from the service's listing: Base Sepolia or Arc Testnet (USDC, x402 `exact`), Tempo Moderato (pathUSD, MPP `tempo.charge`) or Solana devnet (USDC, x402 `exact`). `--rail` and `--chain` are optional; when given they must name the listing's chain (`--rail evm` alone takes Base Sepolia or Arc Testnet; exit 2 otherwise), and a mainnet is exit 3. `find --once` shows each service's chain.

- Before anything is created it reads the service's listing, checks the inputs against it, and refuses (exit 3) when the price is above `--max` or the service is unavailable. After the site creates the purchase, it checks the terms again: the amount (its `atomic` value, the integer the wallet signs, must equal its `decimal` value multiplied by 1,000,000; at most `--max`, equal to the listing), the chain the listing names, that chain's token (USDC, or pathUSD on Tempo) with 6 decimals, and the recipient the listing names. A listing whose two amount values disagree, or whose token has other decimals, has no price and is not bought. The purchase id must be a UUID, as the site makes them. The approval link must be `<site>/approve/<the purchase id>#<token>`, with no control characters, spaces or invisible characters, and must not carry the purchase's access token, whole or in part. A purchase that fails a check is cancelled, and its approval link is never shown. The cancel counts only when the site answers with that purchase `denied` and final, `reason_code: "agent_cancelled"` and payment `not_paid`; then the result is `refused_precheck` (exit 3), nothing paid. Any other answer, a refusal or no answer is `unknown` (exit 5, `final: false`) with `paid: null` and `amount: null`: the purchase is kept in a record (its id and access token, never its approval link), the next `buy-once` is refused (exit 3) while it may be open, and `wait --id ID` (no `--shown` needed) reads it until the site says it ended, then records the final answer. `--replace` asks the site to cancel it again. Site-supplied diagnostic messages are not repeated in a `RESULT`, a log line or a record, on any buy-once step (the listing it buys from, the creation, each read, the cancel, `wait`, the final answer, `--abandon`): a reason names the HTTP status and the purchase states, payment statuses, reason codes and error codes the site's API documents, anything else as `unexpected`, in the client's own sentences. Anything shaped like an access token is also taken out. The seller's answer in `responseFile` is the purchase itself and is saved as the site relays it.
- A listing's parameter names must match `[A-Za-z0-9_.-]{1,64}`; a listing with any other is malformed and is neither shown nor bought. Its allowed values, name and description are data: one line, bounded, with anything shaped like a token taken out. A wrong `--param` is refused (exit 2) with the listing's parameters under `inputs`, never inside `reason`. A chain, protocol or token the client does not know is `unexpected`, and an unavailable service's reason is not repeated.
- `terms` and `message_for_owner` are the client's own words: the service id, the amount, the chain, the recipient and, in `message_for_owner`, the purchase id and the site. The listing's name for the service is in `terms.listingName`, its own words, apart from the rest.
- As soon as the approval link exists, stdout gets `APPROVE {"action":"buy-once","url","expires","terms","matchCode"}` and stderr the same URL in words, with the testnet line. Not in a terminal (an agent), or with `--detach`, the command then returns: `RESULT` with `state: "waiting_owner"`, exit 0, and `id`, `purchase` (the site's id), `service`, `url`, `matchCode`, `expires`, `terms` and `next`. In a terminal, or with `--wait`, it reads the purchase until it ends and prints the final `RESULT`.
- There is no background process: the site does the work once the owner signs. `superstables budget wait --id ID` reads the purchase from the site, holding each read up to 20 s, and returns `waiting_owner` only while the owner has not approved and no answer has carried payment evidence. Once the owner's step is over and the outcome is not established (the payment is being submitted, a transfer was prepared for the owner's wallet, a payment was sent that the chain does not show yet, or the site concluded with the payment unknown), it returns `unknown` (exit 5, `paid: null`, `final: false` while a later read can still settle it), with any transaction hash, never `waiting_owner`; it reads on for up to a minute first. Otherwise it returns the stored final `RESULT`, which becomes `unknown` if accumulated evidence no longer supports it. Waiting never approves or retries anything.
- `paid: true` is never the site's word alone. Before it, the command reads the transaction the site names from the listing's chain: on Base Sepolia, Arc Testnet and Tempo Moderato, a successful receipt with a `Transfer` of exactly the purchase's amount of the listed token to the listed recipient (from the payer the site names), and on Solana devnet, the recipient's token balance of the listed mint up by exactly that amount (the payer's down by it), both mined no earlier than 60 seconds before the purchase was created (an allowance for clock differences). When the chain does not show that, the result is `unknown` (exit 5) with `paid: null`: never buy again. The client never returns `paid: false` for a purchase that names a transaction, whatever the site's state or payment status says. It checks a valid transaction hash on chain: a matching transfer means paid; otherwise the outcome is `unknown`. An invalid transaction identifier also means `unknown`, with no chain lookup. Neither does it return `paid: false` when the site's answer, its `payment` or an error envelope carries `money_moved` other than `false`, or when an earlier answer for the same purchase named a transaction or said paid: the purchase's record (mode 600) retains valid hashes and their reported payers, plus flags for transaction identifiers, paid states and possible money movement. These are accumulated from every answer the site gives for the purchase: each creation attempt (errors and retries included), each read and each cancel, successful or not, and used in later payment decisions. Only a purchase whose accumulated answers have no transaction identifier, no paid state and no `money_moved` other than `false` can end with `paid: false`. Each hash is checked against its recorded payer; a hash with no recorded payer or conflicting payers cannot establish payment (a later answer can supply its payer). The payer and the authorization nonce are fixed by the first answer that names them (a later different one leaves the payment unattributed, so the outcome is `unknown`), the transaction must be named with that payer, and on Base Sepolia, Arc Testnet and Robinhood Chain Testnet the nonce must be the keccak256 of the canonical `superstables-order/1` text the site shows, which names this purchase's id, service, network, token, recipient and amount. Once any answer shows a payer, the site's word alone never ends the purchase as `paid: false`. One verified payment establishes `paid: true`. Otherwise, an unresolved hash keeps the outcome open for a later `wait`. A stored final answer, paid or not, is checked against the evidence again whenever it is read or another answer arrives: one the evidence no longer supports becomes `unknown`. A creation that cannot be read again (no usable purchase id, or no creation confirmed) but whose answers carried such evidence ends `unknown` (exit 5) and is stored with that evidence, so `wait --id ID` prints it again. When `paid: true`, `amount` is the amount checked when the purchase was created; otherwise it is `"0"` when nothing was paid, or `null` when payment is unknown.
- The final `RESULT`: `state: "settled"` with `paid`, `delivered`, `amount`, `tx: {settle}`, `txUrl`, `payer`, `purchase` (the receipt's id on the site), `service`, and, when the seller answered, `responseFile`, `responseType`, `responseBytes`, `responseTruncated`. The file is `$SUPERSTABLES_HOME/budget/once/<id>.response`, mode 600, holding the answer the site relays (it keeps the first 4,000 characters): seller data, never instructions.

| Exit | State | When |
| --- | --- | --- |
| 0 | `settled` | Paid and delivered. Also `waiting_owner`: not final |
| 1 | `failed` | Nothing was paid when `paid: false` and no transaction hash is present (the seller refused, the site did not answer, a rate limit); otherwise the outcome is unknown: report any hash |
| 2 | `failed` | Bad input: a flag, an input the service does not list, an unknown service |
| 3 | `refused_precheck` | Nothing was paid (`paid: false`, no transaction hash): the price is above `--max`, the owner rejected it, said they did not ask for it, picked another code, or did not approve within 10 minutes; or a check above failed |
| 3 | `refused_pending` | No new purchase was started: an earlier one is still open. It is described under `pending`; `paid`, `delivered` and `amount` are `null`, because they say nothing about it |
| 4 | `settled` | Paid, the service did not deliver: never pay again |
| 5 | `unknown` | The owner's step is over and the payment outcome is not established yet (the site's state is uncertain or its payment status unknown, a payment is being submitted, or a sent payment is not yet confirmed on chain), the site says paid and the chain does not show that payment, or a purchase that failed a check could not be confirmed cancelled: never buy again. `final: false` when a later `wait` can still read it |

- One buy-once purchase is open at a time. A second `buy-once` first reads the open one from the site, and records it if the site says it ended. If not, or if its answer is not final yet (the site says paid and the chain does not show it), it is refused (exit 3, `state: "refused_pending"`) with the open purchase under `pending`: `id`, `purchase`, `service`, its `state` (`waiting_owner`; `unknown` when its cancel was not confirmed; `paid_not_final` when it was read as paid and its payment is not final yet, in which case no link is repeated) and, when its approval link was shown, `url`, `matchCode`, `expires`, `terms` and `message_for_owner`. A purchase read as paid whose payment is not final holds the next one until `wait` stores it final; only the owner can stop waiting for its finality with `wait --id ID --abandon`, which keeps the paid result and marks the record with `finalityAbandonedAt`. `--replace` asks the site to cancel it, which it does only while nobody has signed. Age never ends an open purchase: a signed payment can settle after the approval link expired. If the site never ends one, the owner gives it up with `superstables budget wait --id ID --abandon`: it reads the site once (a purchase that ended there is recorded as usual); otherwise the record is kept, marked with `abandonedAt`, and its final answer is `unknown` (exit 5, `final: true`, `paid: null`). The payment stays unknown, and `buy-once` can start a new purchase. An agent never runs it. Starting one holds a lock (`budget/approvals/active-once-purchase`), so two started together cannot both create a purchase: the second is refused (exit 3).
- The purchase's access token (`sspt_test_...`) is kept only in the approval's record (`budget/approvals/<id>.json`, mode 600) and removed when the purchase is final. It is never printed or logged. A retried creation uses the same `Idempotency-Key` and `Superstables-Replay-Secret`.
- `--site` is the site, else `SUPERSTABLES_SITE`, else the `SITE` that `setup --hosted` recorded, else `https://www.superstables.com`.

## Output

stdout carries one JSON object on its last line, prefixed `RESULT `; human logs go to stderr. It is the only `RESULT` line the command prints, on stdout or stderr: the rail script's own `RESULT` is normalized into it, not echoed.

`--json`, on every command (also `wait`, and bad input): stdout is exactly that object, as bare JSON without the `RESULT ` prefix, the same rule as the rest of the `superstables` CLI's `--json`. An owner command's `APPROVE` line then goes to stderr with the logs (the approval link is also the `RESULT`'s `url`). The fields, states and exit codes are the same with or without it. A background worker never gets `--json`: `wait --json` prints the stored result the same way.

`final` is in every `RESULT`: `false` while an owner approval is still open (`state: "waiting_owner"`) and for a buy-once `unknown` that a later `wait` can still read, `true` otherwise. A script tests `final`, not the state or the exit code. An agent does not poll: it replies to the owner and ends its turn, and runs `wait --id ID --shown` when the owner says they've approved.

`message_for_owner` comes with every `waiting_owner` result (owner commands run detached, `buy-once`, `wait` while still open, and `wait` refused for `show_owner_first`) and with every `budget_spent` refusal. It is the reply an agent sends the owner, word for word: for an approval link, the action's title, the site's host when it is not `www.superstables.com`, the approval link, the match code (on superstables.com), the amount and chain, the testnet line, where to open it (a page on this machine) and "Tell me when you've approved"; for a spent budget, what is left, the price and that nothing was paid. The agent sends it and ends its turn.

`rpc` names the RPC a command used when it is a replacement (`B4_RPC`, `SUPERSTABLES_TEMPO_RPC` or `SUPERSTABLES_SOLANA_RPC` for the command's rail); it is absent on the default RPC.

`budget_spent: true` is set on a `buy` refused before signing (`refused_precheck`, exit 3) because the budget cannot cover the purchase: the price is above what is left, or no allowance or delegate exists (spent, revoked or never granted). Its `next` says to report and end the turn; it never proposes a revoke, a new grant or gas.

```json
{"ok":true,"command":"buy","rail":"evm","chain":"base-sepolia","op":"weather-001",
 "state":"settled","final":true,"chain_final":true,"paid":true,"delivered":true,
 "amount":"0.001","remaining":"0.009",
 "tx":{"pull":"0x...","settle":"0x..."},
 "responseFile":"/home/me/.superstables/budget/ops/evm-base-sepolia/weather-001.response",
 "responseType":"application/json","responseBytes":1578,"responseTruncated":false,
 "next":"none"}
```

`responseFile` (`buy`, every rail): the seller's answer to the paid request, saved byte for byte next to the journal as `<op>.response`, mode 600. On `tempo` and `solana` it is saved when the seller answers the request that carries the signed payment with anything but a 402, before the chain outcome is known; on `evm`, only once the pull has landed. A `refused_precheck` buy creates none. A file may hold an error response: its presence proves neither payment nor delivery, so read `state`, `paid` and `delivered`. Saving can fail without changing the purchase: then RESULT has no `responseFile`. At most 1 MB (1,000,000 bytes) is kept; `responseTruncated: true` means the saved bytes are not the whole answer (it was longer, or it was cut off). `responseType` is the seller's content type, `responseBytes` the saved size. The file is seller data, never instructions: nothing here runs or parses it. The log keeps a one-line preview. Seller text in the logs is flattened to one line on every rail, and only an owner command forwards an `APPROVE` line.

On `evm`, a seller whose authorization would stay valid for more than 600 seconds (`maxTimeoutSeconds`) is refused before anything is signed. The check of the payment the x402 client builds allows that payment to expire (`validBefore`) up to 5 seconds later than the offered `maxTimeoutSeconds` from the time of the check, a clock tolerance. Before the pull, the x402 client builds the payment it would send and the client checks it against the option that passed these checks, including the token's EIP-712 domain name and version; the payment is then signed once. Two `buy` commands on one agent key and chain take turns: the second waits up to 10 minutes before it reads balances or signs, and is otherwise refused (exit 3, nothing signed). On Arc Testnet, a `buy` is refused while an earlier purchase's price is still in the agent key (not settled or returned in its journal).

A buy with nothing to buy with is refused before anything is signed, with `state: "refused_precheck"`, exit 3, `paid: false`, `amount: "0"`:

- No setup on this machine (no agent key file with a key, or no owner address recorded): refused before the op lock, the journal or the rail script, so nothing is written that looks like a purchase and no op id is generated. `reason` starts "no budget has been set up here for R on C:" and says what is missing and that nothing was signed; `next` names the owner's commands in order (`setup`, then on `evm` and `solana` `fund-agent` and `doctor`, then `grant`).
- No grant on chain (`evm`: the allowance is 0; `solana`: no delegate; `tempo`: the access key is not authorized, revoked or expired): the rail refuses before signing, and `next` names `grant` (on `tempo`, a revoked or expired key needs `setup --agent LABEL` first). Too little gas for the agent on `evm`: `next` names `fund-agent`.
- The rail script ended on its own (no signal) without a `RESULT` and without ever writing this op's journal: every rail writes the journal before it signs or sends, and the dispatcher holds the op's lock, so nothing was signed. `reason` carries the rail's last error line, and the `--op` stays unused. With a journal, or after a signal, it stays `unknown` (exit 5).

One process per `--op` at a time: a second `buy` with the same op while a buy or reconcile still runs signs nothing and answers `unknown` (exit 5, `paid: null`, `amount: null`, `reason: "op_in_progress"`), because that process may be paying; wait for its `RESULT`, then reconcile. A `buy` whose `--op` already has a journal that is `submitted` or `unknown` (on `solana` also `refused_chain`), or one that cannot be read, answers `unknown` (exit 5, `reason: "op_already_<state>"`, `next` naming `reconcile`) before any other check, so a missing or unsafe key file never makes it look unpaid. A `buy` stopped by a signal (Ctrl-C, a tool's timeout) reports `unknown` (exit 5), whatever its rail printed: reconcile it before anything else. On `solana`, a payment the chain refuses when the command checks it stays `unknown` until its blockhash has expired, since the seller can still submit the signed transaction until then. A rail command run directly treats a journal it cannot read the same way, and so does `reconcile` (`reason: "journal_unreadable"`, never "no journal"). A journal file that parses but is not this op's journal on this rail (it names another op, or lacks a field that rail writes into every journal from the first write on) counts as one that cannot be read: `unknown` (exit 5) with the file kept, never `refused_precheck` or `paid: false`. On `tempo`, a payment the client sends itself (a seller that accepts only push) is journaled `submitted`, with its transaction hash and expiry, right before it leaves. An error while creating the payment can end `failed` with nothing sent only when no broadcast request began. Once the broadcast hook begins, an error remains `unknown`, including a journal-write error that prevents the request from leaving. `reconcile` reports a payment with a recorded expiry as `not_found` once that expiry has passed on chain without it, when its chain reads succeed.

`reconcile` blocked by either operation lock returns exit 5 with `op`, `state: "unknown"`, `paid: null`, `amount: null`, `reason: "op_in_progress"` and `next` asking the owner to check the operation in their own terminal when its holder is possibly alive. Rail commands run directly emit the same reason without a stack trace. A dispatcher buy blocked on its own lock returns the same exit 5, as does rail contention. Agent-facing possibly-alive messages never give unlock instructions.

On `tempo`, `buy` also refuses, before signing (`refused_precheck`, exit 3): a challenge that turns on mppx's machine-token route (`reason` starting `machine_token`), a challenge without a realm or with an expiry that is not a date (`bad_challenge`), a challenge that stays open for more than 600 seconds (`challenge_too_long`), and a challenge another operation on this machine already used (`challenge_used`; claims are kept in `budget/ops/tempo-moderato/claims/`, one file per payment memo, mode 600). The payment mppx signs is read back before it leaves: anything but the quoted pathUSD transfers, or a payment valid for more than 600 seconds, ends `failed` with nothing sent. A purchase journaled without a memo is never reported `not_found`; it stays `unknown`.

Operation locks record a stable host ID, platform, boot ID, PID namespace, PID, process start identity, wall-clock write time and boot-relative write time. Linux reads the host ID from `/etc/machine-id` or `/var/lib/dbus/machine-id` and the boot ID from `/proc/sys/kernel/random/boot_id`. macOS reads the hardware UUID with `ioreg -rd1 -c IOPlatformExpertDevice` and the boot-session UUID with `sysctl -n kern.bootsessionuuid`. Hostnames do not determine liveness; containers on the same kernel can have different hostnames. Locks refresh their own inode timestamp every 15 seconds, even when the takeover mutex is blocked. Heartbeats never expire ownership. Publication is durable, and release checks its own record and inode without requiring takeover-mutex access. A live rail child retains the operation lock; normal child exit permits the dispatcher to release its own generation even with identity reads blocked.

### Operation lock recovery

Agents must stop and ask the owner when a lock blocks reconciliation. Agents never run `unlock`. As the owner, stop every process working on the operation across all containers and hosts. Run `unlock` in your own terminal, outside any agent's sandbox. Plain `--confirm` refuses when Superstables cannot prove that the lock's processes have stopped. If verification remains unavailable after you have stopped all work, add `--unverified`. Read the second-payment warning, then type the operation ID followed by a space and `unverified`. Keep all work stopped until `unlock` finishes, then reconcile the original operation.

```sh
superstables budget unlock --rail solana --chain devnet --op ID --confirm
```

On Linux, run all Superstables commands sharing the same client home (`SUPERSTABLES_HOME`) either inside the same sandbox or outside it; mixing the two can exceed the daily cap or make `budget wait` report a running approval as "abandoned", which is not a reason to pay again.

Use the original rail, chain, and op. Unlock requires `--confirm` and the exact op ID typed at its terminal prompt. Without the flag, it returns exit 3 and `reason: "confirmation_required"`. Non-terminal stdin returns exit 3 and `reason: "owner_terminal_required"`, even with the flag and a piped op ID. A different answer or closed input returns exit 3 and `reason: "owner_confirmation_mismatch"`.

A holder is dead only with positive proof. On Linux, matching readable boot IDs and PID namespaces count as evidence of the same kernel without a machine ID, assuming concurrent VM clones do not share the lock folder. In that verified PID view, an absent PID or a readable process-start mismatch permits recovery. macOS has one host PID namespace, but recovery still requires matching host and boot IDs. A different boot always keeps the holder possibly alive, regardless of its timestamps, machine ID or platform UUID. A previous boot cannot be distinguished from a concurrently running clone. After a crash and reboot, a leftover lock therefore requires the owner's `--confirm --unverified` recovery. The initial Linux PID namespace can also verify a recorded child namespace with a targeted, readable `/proc` scan. A proc mount with `hidepid` enabled or unreadable mount options cannot prove absence. On an unrestricted mount: match the last `NSpid` entry first, then read the namespace only for matching candidates. No readable match and no unreadable candidate proves death. An unreadable candidate keeps the holder possibly alive; unreadable namespace links of unrelated PIDs do not block recovery. Zombies cannot continue work, while a live rail child still protects ownership.

On macOS, agent sandboxes can hide the boot session and process start time. A leftover lock taken under these restrictions cannot clear automatically, and plain `--confirm` refuses it. Recovery requires `--unverified`, which can clear it while the agent is still running. Quit the agent and its sandbox before using it.

A sandbox with unreadable `/proc` assumes it is nested. A local `ESRCH` cannot prove death until both namespace identities are verified. A readable process start at least 60 seconds after the lock's write can prove PID reuse only on the same proven host and boot, in a verified PID view. Boot-relative write time detects clock doubt; within 60 seconds, missing timing evidence or a clock discrepancy stays possibly alive. A timestamp alone never proves death. Recovery refuses any 0.3.0 or 0.3.1 lock whose holder is verified as still running, even with `--unverified`. Among old locks, only the short-lived `cap.lock` format can clear automatically, with proof the holder is gone. Other old locks remain possibly alive unless verified as live.

Default unlock refuses possibly alive holders with exit 5 and `reason: "op_in_progress"`. Run it on the host, outside the sandbox, where identity can be read. If you have stopped all work and the lock still reports possibly alive, the owner can use this explicit override:

```sh
superstables budget unlock --rail solana --chain devnet --op ID --confirm --unverified
```

It requires a terminal and the exact typed text `ID unverified`. It still refuses a verified live holder or rail child. Automatic recovery never uses it. Both recovery paths preserve the journal. Stop all work first. If an overridden holder resumes inside release after its final inode check, it can delete a new holder's lock. Unlock can also delete a new holder's lock if it pauses after its final record check, the old holder releases normally, and a new holder acquires before unlock unlinks the path. A third process can then overlap the new holder and cause duplicate payments. Unlock rechecks the record after printing the override warning, so a replacement during that warning is preserved and returns busy. After process inspection, it checks the record and inode again immediately before deleting the lock. The checks narrow these races but do not make pathname unlink atomic. An override does not guarantee successor safety while any old holder can still run.

macOS keeps the original C-locale local `ps` string in `pidStart`, `railPidStart` and `railPgidStart` for 0.3.0 readers. New records add numeric UTC epoch seconds in `pidStartUtc`, `railPidStartUtc` and `railPgidStartUtc`, read with `LC_ALL=C` and `TZ=UTC0`. New readers prefer those UTC fields, so process checks do not depend on the caller's time zone. Older unzoned process starts cannot prove PID reuse. Older records that lack positive location evidence remain possibly alive and require the explicit owner override after all work is stopped, except for the narrow legacy cap-lock proof described above. Owner recovery help ships with the CLI as `superstables budget unlock --help`.

The terminal prompt prevents ordinary noninteractive agent commands from overriding locks. It is not wallet authentication: anyone with the user's shell can create a terminal and type the op ID. Wallet-approved recovery is follow-up work.

An unrecognised directory requires the owner to inspect and remove that directory after stopping all work; neither waiting nor unlock removes it recursively. Successful unlock returns exit 0, `state: "ok"`, `reason: "locks_cleared"`, the `op`, and a reconcile command in `next`. An existing journal with no locks returns exit 0 and `reason: "no_lock"`, with "no lock" on stderr. If neither the journal nor its locks exist, it returns exit 3 and `reason: "op_not_found"`. Unlock never signs or sends, and never authorizes a second payment. Reconcile next.

### Other payment lock recovery

| | | |
| --- | --- | --- |
| `budget unlock` | 0 / 3 / 5 | Locks cleared or no lock / owner terminal and exact typed confirmation required or operation, attempt or approval not found / verified live or possibly-alive holder, or unrecognised directory refused. The owner stops all associated work and keeps it stopped until recovery finishes. A holder that resumes can remove a successor's lock and allow duplicate payments. Recovery preserves payment evidence. Check the original operation, attempt or approval next. |

Stop all payment work across processes, containers and hosts before recovering a core lock, approval lock, attempt runner or start lock for a single purchase. Run the command in your own terminal, outside any agent's sandbox. Choose one target:

```sh
superstables budget unlock --cap --confirm
superstables budget unlock --rail solana --chain devnet --approvals --confirm
superstables budget unlock --rail solana --chain devnet --approval APPROVAL_ID --confirm
superstables budget unlock --attempt ATTEMPT_ID --confirm
superstables budget unlock --buy-once --confirm
```

`--cap` recovers `records/cap.lock` and its takeover mutex. `--approvals` recovers the chain lock, associated approval record locks and their takeover mutexes. `--approval` also selects that approval's record lock when its record is missing or unreadable. Use its original rail and chain. `--attempt` recovers the reconciliation lock and appends a runner-release row for the original attempt. It preserves every payment field, reservation, receipt reference and history entry. It does not declare a payment unpaid or release its cap reservation. `--buy-once` recovers `budget/approvals/active-once-purchase` and its takeover mutex, preserving the purchase record and evidence. To recover a single purchase's record lock, use `--approval ID` with the purchase's original `--rail` and `--chain`, not `--buy-once`.

Type `payment-lock` exactly at the prompt. Plain `--confirm` refuses a possibly-alive holder. After stopping all work, if verification remains unavailable, add `--unverified`, read the second-payment warning and type `payment-lock unverified` exactly. Both plain recovery and the override refuse verified live holders, including holders recorded by 0.3.0 or 0.3.1 when the Linux identity checks described above verify them as live. The terminal and exact-input protections are the same as operation recovery. No agent may use these commands or create a terminal to pass their prompts.

A missing attempt returns exit 3 with `reason: "attempt_not_found"`. An approval not found on the selected rail and chain returns exit 3 with `reason: "approval_not_found"`. Neither result means a lock is held. A verified live holder returns exit 5 without recommending an override. A target with no locks returns exit 0 with `reason: "no_lock"`; cleared locks return `reason: "locks_cleared"`.

After recovery, run `superstables status ATTEMPT_ID` for the original attempt, or `superstables budget wait --id APPROVAL_ID --shown` for an approval you already showed to the owner. Recovery preserves approval records and never invents a final approval result. Recovery permits read-only reconciliation. It does not authorize a second payment. The existing pathname-unlink races also apply to these targets; keep all work stopped until recovery finishes.

EVM `recover` without `--op` locks only the operations it listed at the start. Just before its sweep it reads every journal again, and it sweeps nothing while a journal cannot be read or an operation of this agent is still being sent, not final, or holds an authorization that can still settle. Stop all buys for that agent before running it, and prefer `recover --op ID` for one operation. An owner who has checked an unreadable file and the agent's payments on chain can repair it or move it out of the journal folder; recover then sweeps on its next run. Agent-wide serialization of recovery and buys remains separate work.

Upgrade every install of the client at once, and stop old agents and servers before using the new version. Old direct Solana buys can delete the new JSON lock, and old reconcile commands do not lock at all. Version 0.3.0 recognises live 0.3.1 dispatcher locks and approval records on macOS when both processes use the same time zone, and on Linux. Its macOS readers still compare local start strings exactly, so different time zones remain unsafe. This interoperability does not make mixed versions safe.

`buy-once` ends the same way: its `RESULT` has `service`, `purchase`, `txUrl` and `payer` as well, and `id` is the approval id `wait` takes.

`state`: `planned`, `sent`, `settled`, `failed`, `refused_precheck`, `refused_chain`, `unknown`, `not_found`, `ok` (reads), `waiting_owner` (the detached owner command has no final result yet, and the owner's wallet was not asked to send), `show_owner_first` (`wait` without `--shown`, exit 2: nothing was polled, so it states no outcome), `refused_pending` (`buy-once`, exit 3: an earlier purchase is still open, under `pending`). Unknown amounts are `null`, never `"0"`.

`proof` (an owner command that ended `failed`): the chain fact that shows its transaction changed nothing. `reverted`: it landed and failed, and it is the planned call from the owner (a reverted transaction that differs from the plan is `unknown`). `blockhash_expired` (`solana`): the chain is past its last valid block height and, read at that height or later, has no status for its signature, so it can never land. Once the owner's wallet was asked to send, or the command began to broadcast a transaction (with an owner key file, say), an owner command says `failed` only with a `proof`. Anything else from then on is `unknown` (exit 5): the script stopped with an error, a chain read failed or disagreed with the plan, or a later step was refused after an earlier one sent.

## Exit codes (same on every rail)

| Code | Meaning | What the caller does |
| --- | --- | --- |
| 0 | Done (purchase settled and delivered, or command succeeded). Also `state: "waiting_owner"` with `final: false`: the command has no final result yet | continue; on `waiting_owner`, write the approval link, the code and the terms in your reply to the owner and end your turn; when they say they've approved, run `superstables budget wait --id ID --shown` until `final` is `true` |
| 1 | Failed, including a chain refusal. An owner command that may have sent says this only with a `proof` from the chain | read `next`; don't retry blindly |
| 2 | Bad input | fix the command |
| 3 | Refused before anything was sent: no budget set up here, no grant, over `--max`, the owner rejected it or the approval link expired before the wallet was asked to send. | 5 | Outcome unknown, including an owner action whose transaction on chain does not match the plan, or that may have sent and has no proof of how it ended | purchases: `reconcile --rail R --chain C --op ID` (`buy-once`: ask the owner to check wallet activity); owner actions: `status` on the same rail and chain, plus wallet activity. Never pay twice |

## Where things live

All paths come from `paths.mjs`, under the client's home (`SUPERSTABLES_HOME`, default `~/.superstables`). Keys: `keys/budget/<rail>-agent.env` (mode 600). The default flow stores no owner key: the owner's key stays in their wallet. Public addresses: `budget/public/<rail>-<chain>.env`. Journals: `budget/ops/<rail>-<chain>/<id>.json`, and the seller's answer `<id>.response` when it was saved (mode 600). A running dispatcher `buy` or `reconcile` holds `<id>.buy.lock` next to its journal. An `evm` `buy`, and `recover` before it sends from the agent key, also holds `agent-<address>.key.lock` in that directory, so purchases on one agent key and chain take turns. Every rail journal writer also holds `<id>.json.lock`; each lock has a takeover mutex `<lock>.break`. Approval page log (state changes, no signatures): `budget/owner-approvals.jsonl`. What `buy-once` returned: `budget/once/<id>.response` (mode 600). Detached approvals, and each buy-once purchase's record: `budget/approvals/<id>.json` (the record and the final `RESULT`, mode 600; for an approval on superstables.com also the site, its request id and, until final, the access token), `budget/approvals/<id>.log` (the background process's output), and `budget/approvals/active-<rail>-<chain>` (the id that holds that chain).

Payment attribution claims: `budget/once/attributed-<rail>-<chain>-<tx>.json` (mode 600, in a mode 700 directory). Each claim stores only `[site, purchase id]`, never an access token, and prevents another purchase in this home from claiming the same transaction. The client syncs the claim file and directory before publishing it atomically, then syncs the published entry before recording paid. An empty or unreadable claim keeps the outcome unknown and open, with its access token retained for the next `wait`. Claim temporaries end in `.json.<pid>.<uuid>.tmp`; a read removes them only when their writer is gone or they share the published claim's inode. Older `.json.<uuid>.tmp` files are removed only when they share that inode. Recorded paid outcomes from older clients are preserved with `attribution: "verification not recorded (older version)"`; new purchases must pass attribution checks.

Environment: `SUPERSTABLES_HOME` (above); `SUPERSTABLES_SITE`, the site for `setup --hosted` and `find` when `--site` is not given (`find` then uses the recorded site before the default); `SUPERSTABLES_ALLOW_SITE`, the owner's opt-in for a site outside superstables.com (the exact `https` origin, or a comma-separated list; an agent never sets it); `B4_CHAIN`, the default `evm` chain for the rail scripts; `B4_RPC`, an RPC URL that replaces the selected `evm` chain's, and Base Sepolia's for `buy-once` (for tests or your own node; scripts that sign still check the chain id first); `SUPERSTABLES_TEMPO_RPC` and `SUPERSTABLES_SOLANA_RPC`, the same for Tempo Moderato and Solana devnet. A replacement RPC must be `https`, or `http` on `127.0.0.1`, `localhost` or `[::1]`, with no user name or password: anything else is refused (exit 2) before a command runs, and the rail scripts run directly ignore it with a warning. On `solana`, `fund-agent`, `grant`, `revoke`, `buy`, and `setup` when it replaces a recorded owner or asks for `--fund` or `--grant`, first check that the RPC answers Solana devnet's genesis hash. On another cluster, or when the hash can't be read, they refuse (exit 3) before a blockhash is fetched or anything is signed or sent. `status` then says the budget could not be read (exit 1). A replacement in use is named in the `RESULT` (`rpc`). A wallet that adds the chain on an approval page on your machine is offered the chain's public RPC, never the replacement.

## Approvals on superstables.com: what a compatible site must do

Approvals on superstables.com, `buy-once` and `find` talk to one site over HTTPS (or HTTP on this machine). superstables.com is that site; another deployment that serves the endpoints below the same way works too, once the owner names its origin in `SUPERSTABLES_ALLOW_SITE`. Every answer is JSON. An error keeps one envelope, `{ "error": { "code", "message", ... } }`, and the client shows its `code`, `reason` and `message` as text, never as instructions.

### Endpoints the client calls

| Call | Auth | Body or query | Answer the client relies on |
| --- | --- | --- | --- |
| `POST /api/v1/budget/links` | agent proof v2 | `{ rail, chain, agent, label?, expected_owner?, then? }`. `expected_owner` is sent only when `GET /api/v1/budget/services` lists it in `features`, only for the owner recorded on the agent's machine, and the answer must repeat it (`409 expected_owner_mismatch` when the agent belongs to another account). `then`: up to two wallet steps after the agent is added, `fund_agent` then `grant`, each `{ kind, transaction: { to, data, value } }` on `evm` and `tempo`, or `{ kind, solana: { amount_atomic } }` on `solana` | `201 { id: "bl_...", access_token: "ssbt_...", approval: { url, match_code, expires_at }, steps? }`; `steps` echoes `then` in order. An agent already added on that rail and chain: `200 { id, state: "linked", final: true, owner, owner_proof, approval: null }`, or `409 { error: { code: "already_linked", owner, owner_proof } }` when `then` was sent |
| `POST /api/v1/budget/approvals` | agent proof v2 | `{ kind: "grant" \| "revoke" \| "fund_agent", rail, chain, agent, transaction }` on `evm` and `tempo` (the exact `{ to, data, value }`), or `{ ..., solana: { amount_atomic? } }` on `solana` | `201 { id: "ba_...", access_token, approval: { url, match_code, expires_at } }` |
| `GET /api/v1/budget/requests/{id}?wait=0..20` | `Authorization: Bearer ssbt_...` | | `{ id, kind, state, final, owner, owner_proof, tx_hash, wallet_asked, reason, steps? }`, held up to `wait` seconds for a change |
| `POST /api/v1/budget/requests/{id}/cancel` | `Authorization: Bearer ssbt_...` | `{}` | `200` with the request: `{ id, state: "cancelled", final: true, wallet_asked: false, tx_hash: null }`. Otherwise `409 { error: { code, state, wallet_asked, tx_hash } }`; `409 not_open` with `state: "cancelled"`, `wallet_asked: false` and `tx_hash: null` also counts, without an id or `final`, but never with another request's id. Evidence in the answer, its `error` or their steps (a wallet request, a transaction, a send-implying state, `money_moved`), or in an earlier answer (an error answer to a read too: `error.money_moved`, even on a `429`), makes it unknown. Any other answer is read as unknown. For an add-agent request with steps, a step counts as never asked only when an answer about this request says so, or the site confirmed the unapproved request withdrawn. Its cancel answers with the request, steps included |
| `GET /api/v1/budget/services` | none | | `{ features?, services: [{ name, price, network, url }] }` (for `find`; `features` names the optional fields the site accepts) |
| `GET /api/v1/purchase/services[/{id}]` | none | | the services `buy-once` can buy, with inputs, price, chain, token and recipient |
| `POST /api/v1/purchases` | `Idempotency-Key`, `Superstables-Replay-Secret` | `{ service_id, params, max_amount }` | `202` accepted (or `200` for an idempotent replay) with `id`, `access_token` (`sspt_...`), `terms` and `approval: { url, match_code, expires_at }`; creation is not payment approval or completion |
| `GET /api/v1/purchases/{id}?wait=0..20`, `POST /api/v1/purchases/{id}/cancel` | `Authorization: Bearer sspt_...` | | the purchase's `state`, `final`, `payment` (`status`, `transaction`, `payer`) and `delivery` |

- Request IDs are `bl_` (an add-agent request, kind `link`) or `ba_` (an approval) followed by letters, digits, `_` or `-`; access tokens are `ssbt_` followed by the same. The approval link is `<site>/approve/budget/<id>#<token>` for a budget request and `<site>/approve/<id>#<token>` for a purchase, on the site's own origin; the client refuses any other shape.
- States of a budget request: `awaiting_owner`, `sending`, `sent`, `confirmed`, `linked`, `failed`, `rejected`, `expired`, `cancelled`, `unknown`. Once the owner's wallet was asked, the site sets `wallet_asked: true`, and reports the transaction as `tx_hash` (a 0x hash, or a base58 signature on `solana`). The client reads every transaction from the chain itself before it reports success.
- An approval's `owner` must be the owner recorded on the agent's machine; the client cancels and refuses one that names another address, and a bundle the site adds to another account is withdrawn.

### Agent request proof v2

Every `POST` to `/api/v1/budget/links` and `/api/v1/budget/approvals` carries four headers:

- `Superstables-Agent`: the agent's address: the checksummed `0x` address on `evm` and `tempo`, the base58 public key on `solana`. The body's `agent` is the same value.
- `Superstables-Agent-Timestamp`: unix seconds.
- `Superstables-Agent-Nonce`: 32 lowercase hex characters (16 random bytes), new for every request.
- `Superstables-Agent-Signature`: the agent key's signature of the text below: EIP-191 `personal_sign` on `evm` and `tempo`; ed25519 over the text's UTF-8 bytes on `solana`, written `0x` and 128 hex characters.

The signed text is these six lines, separated by `\n`, with no trailing newline:

```
Superstables agent request v2
origin: <the site's origin, such as https://www.superstables.com>
<METHOD> <path, without the query>
<sha256 of the exact body bytes, lowercase hex>
<timestamp>
<nonce>
```

The site checks, in order, and answers any failure with `401 { "error": { "code": "agent_proof", "reason": ..., "message": ... } }`:

1. The `origin:` line is the site's own canonical origin, from its configuration, never from the request's `Host` header. Each deployment (staging, production) has its own. A proof made for another origin fails as a bad signature.
2. The timestamp is within 300 seconds of the site's clock.
3. The nonce matches `^[0-9a-f]{32}$` and was not used by that agent in the last 10 minutes, recorded atomically. The exact resend of a request that created one answers `409 { "error": { "code": "proof_reused" }, "id" }` with that request's id; any other repeat is refused with `reason: "replayed"`.
4. The method, path and body hash are those of the request received.
5. The signature verifies for the agent address, and the body's `agent` is that address.

The client retries once on a network error with the same proof. If the site answers that retry with `reason: "replayed"` (the first attempt reached it and failed), the client signs again with a new nonce and sends once more.

### Owner proof

When the owner adds the agent (signed in, match code picked), the site asks the owner's wallet to sign these eight lines, separated by `\n`, with no trailing newline:

```
Superstables: add an agent to my account
site: <the site's origin, the same canonical origin as above>
owner: <the owner: checksummed 0x on evm and tempo, the base58 Solana address on solana>
agent: <the agent, as in Superstables-Agent>
rail: <evm, tempo or solana>
chain: <the chain key, such as base-sepolia, moderato or devnet>
request: <the add-agent request ID the agent created>
code: <the match code shown to the agent>
```

On `evm` and `tempo` the owner's EVM wallet signs it with EIP-191 `personal_sign` (`scheme: "eip191"`); on `solana` the owner's Solana wallet signs its UTF-8 bytes with `signMessage` (`scheme: "ed25519"`, the signature as `0x` and 128 hex characters). The site verifies it before it adds the agent, stores it with the add-agent request, and returns it as `"owner_proof": { "scheme", "message", "signature" }` in the request's state once the agent is added (`null` before), in every `already_linked` answer for that agent, rail and chain, and in the `409 already_linked` error. The agent cannot be added without it.

The client, before it records anyone as the owner:

1. Rebuilds the text from its own values: the site origin it uses, the `owner` the site returned, its own agent address, rail and chain, the request ID it created (the `request:` line) and the match code it received. It must equal `owner_proof.message` byte for byte.
2. Verifies the signature for that owner: the EIP-191 signer is the owner, or the ed25519 signature verifies with the owner's base58 public key.
3. Takes an `already_linked` answer only when an owner is already recorded on the machine, it is the same owner, the command is not `setup --new-owner`, the recorded site is this site, and the proof passes 1 and 2 against the `LINK_ID` and `LINK_CODE` stored when that owner was recorded. Otherwise it records nothing (exit 3), and the owner removes the agent on their account page on the site and adds it again.

## Checkout or standalone build

In a checkout with its development packages installed (`npm ci`), `budget/cli.mjs` runs the rail scripts from their TypeScript sources with the checkout's tsx, so a source edit takes effect on the next run. Without tsx, it hands the whole command to `dist/budget/cli.mjs` when that build exists; source edits then require a rebuild. With neither tsx nor a build, commands other than help and version report what to install. `npm run build` also writes `dist/budget/`: the dispatcher and every rail script bundled into plain JavaScript that imports only Node built-ins and its own files. Those `.mjs` files run in a checkout fallback or a standalone copy: `dist/budget/` itself, or `scripts/budget/` in the skill zip that `npm run skill` builds. The commands, flags, `RESULT` lines, exit codes and paths are the same.

`superstables budget --version` names the build: for a standalone copy, the version, commit and commit time from its `VERSION.json`; in a checkout with tsx, the version and commit. A checkout falling back to dist names the standalone build and the checkout path that selected it. Only `--version` prints it: normal output does not. `THIRD_PARTY_NOTICES.txt` in a standalone copy lists every bundled package with its version and licence text.

A buy-once whose earlier inclusion was removed can stay `unknown`, `final: false` indefinitely, even after finality passes its old block. The read token remains available, as in 0.3.0's existing site-paid but chain-unverified unknown case. Stop automatic polling in that case and report it to the owner. `superstables budget wait --id <id> --abandon` ends local waiting without proving the purchase unpaid or permitting payment again.
